## Critical (all verified)

### Settlement API trusts client-supplied gross_fare: any authenticated user can mint driver wallet credit

- **Area:** money · **Location:** `internal/settlement/application/settlement_service.go:90` · **Confidence:** high
- **Evidence:** internal/settlement/application/settlement_service.go:88-92: 	settlement := domain.CalculateSettlement( 		settlementID, tenantID, req.TripID, req.DriverID, 		req.GrossFare, req.TollAdjustment, req.AdvanceDeductions, 		req.CommissionRate, req.TDSRate, 	) req is decoded straight from the request body with no server-side derivation (settlement_handler.go:56-59 `json.NewDecoder(r.Body).Decode(&req)`), the service then immediately credits the ledger with `gross: settlement.GrossFare` (settlement_service.go:111), and the route is registered with no permission middleware at all: settlement_handler.go:27 `r.Post("/settlements/calculate", h.CalculateSettlement)` (only RequireAPIAuth wraps the group, cmd/server/main.go:1057).
- **Impact:** Any logged-in user, including a driver, can POST {trip_id:"anything", driver_id:"<self or any driver>", gross_fare:10000000, toll_adjustment:0} to /api/v1/settlements/calculate. No trip existence, trip ownership, driver match, or role check is performed, and the settlement is committed with a TRIP_EARNING ledger credit of the attacker-chosen gross. The driver's AvailableBalance (last driver_ledger_entries.balance_after) then shows the fabricated amount, and with PAYOUT_RAIL_ENABLED the same driver can immediately request a payout for it via /api/v1/drivers/me/payouts. Even with the rail off, every wallet/reporting/accounting figure is corrupted with money that was never earned.
- **Fix:** Derive gross fare/commission/deductions server-side from the trip/booking (as the legacy DriverSettlementService.calculateGrossFare does), reject client money fields, verify the trip and driver belong to the caller's tenant (and that the caller is that driver or holds settlements:write), and add RequirePermission(authSvc, "settlements", "write") to /settlements/calculate.
- **Verification:** verified — GrossFare comes from the JSON body; /api/v1/settlements/calculate has no permission gate beyond authentication, and it writes driver ledger credit.

### Public Razorpay verify accepts any signature-valid order/payment for any invoice, so a small payment can settle an arbitrary invoice

- **Area:** money · **Location:** `internal/handlers/public_payment.go:309` · **Confidence:** high
- **Evidence:** internal/handlers/public_payment.go:292-315: 	var canonicalID, tenantID string 	err := h.DB.QueryRowContext(r.Context(), ` 		SELECT id, tenant_id FROM invoices WHERE id = $1 OR invoice_number = $2 LIMIT 1 	`, req.InvoiceID, req.InvoiceID).Scan(&canonicalID, &tenantID) 	... 	ctx := shared.ContextWithTenantID(r.Context(), shared.TenantID(tenantID)) 	paymentID, err := h.verifyUC.Execute(ctx, paymentapp.VerifyRazorpayPaymentCommand{ 		TenantID:  shared.TenantID(tenantID), 		InvoiceID: canonicalID, 		OrderID:   req.OrderID, 		PaymentID: req.PaymentID, 		Signature: req.Signature, 	}) req.InvoiceID comes from the unauthenticated JSON body (line 276-278 only falls back to the path), while the only cryptographic check binds orderID+paymentID: razorpay_order.go:135 `if !uc.verifier.VerifyPaymentSignature(cmd.OrderID, cmd.PaymentID, cmd.Signature)` and razorpay/client.go:112 `data := orderID + "\|" + paymentID`. The invoice/tenant is never derived from the signed order or payment.
- **Impact:** Concrete fraud: an attacker creates and pays a Razorpay order for a small invoice (or any invoice they own) and receives the checkout signature for that order_id\|payment_id pair. They then POST that same pair to /pay/<victim>/razorpay/verify with invoice_id set to a victim invoice (body overrides the path). The handler resolves the victim invoice's tenant from the DB, the HMAC over order\|payment still validates, and the use case records a payment for the full victim outstanding balance, marking the victim invoice paid although no money for it was captured. The Razorpay payment.captured webhook later dedups by razorpay_payment_id and returns this same row, so the forged credit is never corrected. Cross-tenant because the tenant is taken from the target invoice row, not the caller.
- **Fix:** Bind the order to the invoice at creation (persist order_id -> invoice_id/tenant at CreateRazorpayOrder) and on verify require that the presented order_id maps to the requested invoice and tenant; additionally fetch the payment from the gateway API and check its order_id/amount/notes.invoice_id before recording.
- **Verification:** verified — Invoice is resolved independently of the Razorpay order; signature covers only order\|payment, so a cheap valid payment can settle any invoice balance.

### Driver-command trip statuses violate the trips.status CHECK, so START_TRIP/ARRIVE_PICKUP/etc. always fail

- **Area:** dispatch · **Location:** `internal/driver/application/dispatch_service.go:307` · **Confidence:** high
- **Evidence:** nextStatus = "en_route_pickup" ... lines 309,311,313,317,319,343 assign "arrived_pickup", "loading", "loaded", "arrived_delivery", "unloading", "trip_interrupted" -- db/schema.sql:2353 (generated from all migrations; same list in migrations/00081 and migrations_pg/00081) status        TEXT NOT NULL DEFAULT 'draft' CHECK (status IN ('draft', 'scheduled', 'assigned', 'started', 'reached_pickup', 'in_transit', 'delivered', 'completed', 'cancelled'))
- **Impact:** POST /api/v1/drivers/me/commands with START_TRIP/EN_ROUTE_PICKUP, ARRIVE_PICKUP, START_LOADING, COMPLETE_LOADING, ARRIVE_DELIVERY, START_UNLOADING or INTERRUPT_TRIP executes `UPDATE trips SET status=$1 ...` with a value the CHECK forbids, so the DB returns `CHECK constraint failed` and the handler answers 422; no driver working the shipped command API can advance a trip past `assigned`. The unit test that asserts `en_route_pickup` works passes only because services_test.go:57-64 creates a trips table with no CHECK. Verified with `sqlite3 :memory:` that `UPDATE trips SET status='arrived_pickup'` fails with the CHECK error.
- **Fix:** Add a migration that rebuilds the trips status CHECK (SQLite) / drops-and-re-adds trips_status_check (PG) to include the full driver lifecycle enum, or map the command set onto the existing allowed statuses; add a regression test built from the real migrations instead of the ad-hoc baseSchema.
- **Verification:** verified — Statuses written here (en_route_pickup, arrived_pickup, loading, loaded, arrived_delivery, unloading, trip_interrupted) are absent from the trips.status CHECK in 00081; UPDATE fails.

### SOS acknowledges "dispatchers alerted" when the outbox insert failed

- **Area:** geofence · **Location:** `internal/handlers/sos.go:177` · **Confidence:** high
- **Evidence:** ```go 	rowsAffected := int64(0) 	if err == nil && res != nil { 		rowsAffected, _ = res.RowsAffected() 	} ```  ```go 	status := http.StatusCreated 	if rowsAffected == 0 { 		status = http.StatusOK // Idempotent duplicate acknowledgment 	}  	httpx.JSON(w, status, SOSResponse{ 		Status:     "acknowledged", ... 		Message:    "Emergency response team and dispatchers have been alerted.", 	}) ```
- **Impact:** If the INSERT fails (DB busy/locked, disk full, context deadline), `err` is set but is never checked and never logged. `rowsAffected` stays 0, so the publish and audit steps are skipped, yet the handler returns HTTP 200 with `"acknowledged"` and the message that dispatchers have been alerted. A driver pressing the panic button is told help is coming while nothing was persisted or published, and no alert, notification, or audit record exists. The same branch is used for genuine idempotent duplicates, so the failure is indistinguishable from a dedupe hit.
- **Fix:** Branch explicitly on `err`: log it and return 5xx/503 with a non-acknowledging message (or retry), and only map `rowsAffected == 0` to the idempotent 200 when `err == nil`.
- **Verification:** verified — outbox INSERT error is ignored; rowsAffected stays 0 but response is 200 "dispatchers have been alerted" and no publish/audit runs.

#### Reflected XSS: login `redirect` value concatenated into an inline script

- **Area:** web · **Category:** security · **Location:** `internal/handlers/auth.go:575` · **Confidence:** high · **Verification:** downgraded
- **Evidence:** Line 575: `_, _ = w.Write([]byte("<script>window.location.href='" + targetURL + "'</script>"))`; targetURL is attacker-controlled at line 568: `if red := shared.SafeRedirect(r.PostFormValue("redirect")); red != "" {`. shared.SafeRedirect (internal/shared/redirect.go:11-22) only rejects leading `//`, absolute URLs, scheme or host — it returns a value containing `'` and `</script>` unchanged. - **Impact:** An attacker auto-submits a cross-site POST to `https://app/login?_fragment=true` with their own valid credentials (a logged-out victim has no session cookie, so CSRFProtectStrict passes) and `redirect=/x'</script><script>alert(document.domain)</script>`. - **Verifier note:** Inline script interpolation is real, but isDatastarRequest needs a Datastar/HX header or _fragment=true plus valid credentials, so practical impact is self-XSS/login CSRF, not high.
